# 多租户架构说明

## 1. 架构目标
多租户（Multi-Tenant）架构旨在让同一套后端服务和数据库，能够安全地服务于多个不同的社区或组织。各社区的数据在物理存储上共享同一数据库，但在逻辑上严格隔离。

## 2. 实现路径

### 2.1 数据库层面
在所有的核心表（包括 `registrations`, `teams`, `matches`, `announcements`）中，新增了 `tenant_id` 字段（默认值为 `'default'`）。
同时，针对战网ID等原本具有全局唯一性的字段，修改了其 `UNIQUE` 约束，将其与 `tenant_id` 绑定。例如，玩家可以在社区A（`tenant_A`）和社区B（`tenant_B`）分别报名，而不会产生冲突。

### 2.2 后端拦截层面
在 Express 后端引入了全局的 `tenantMiddleware` 中间件。该中间件会拦截所有 HTTP 请求，并从请求头中提取 `X-Tenant-Id`。
- 如果请求头未提供，系统会自动回退使用 `'default'` 租户。
- 提取到的 `tenant_id` 会被挂载到 `req.tenantId` 对象上。
- 在后续的路由和 Service 层中，所有的 SQL `SELECT`、`INSERT`、`UPDATE`、`DELETE` 操作，均被强制附加了 `AND tenant_id = $x` 条件。

### 2.3 前端注入层面
前端通过环境变量（`.env`）进行租户标识配置。在前端启动或打包时，系统读取环境配置并注入到 axios 拦截器中，所有向后端的请求都会自动带上 `X-Tenant-Id` Header。

## 3. 使用方法（如何部署新社区）

当您需要为另一个全新的社区部署一套前端时：

1. 复制前端代码，或者直接修改前端目录下的 `.env` 文件。
2. 将 `VITE_TENANT_ID` 的值修改为该社区的专属标识。例如：
   ```env
   VITE_API_BASE_URL=/api
   VITE_TENANT_ID=community_b
   ```
3. 运行 `npm run build` 打包前端，并将其部署到新的域名或子目录下。
4. 后端无需进行任何重启或修改，新部署的前端产生的报名、分队数据将自动归属到 `community_b` 租户下，与其他社区完全隔离。
