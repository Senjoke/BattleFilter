# 开发落地文档总目录结构

本目录用于承载面向开发落地的三类文档：前端、后端、数据库。三份文档对同一名词、同一字段含义、同一流程的描述保持一致，确保从报名到分队到赛程发布再到周期清理能够闭环实施。

## 目录结构

```
文档
└─ 开发落地
   ├─ 总目录结构
   ├─ 前端落地文档
   ├─ 后端落地文档
   └─ 数据库落地文档
```

## 阅读顺序

1. 先读《总目录结构》，理解名词与统一规则
2. 再读三份落地文档，按职责分工拆解任务
3. 最后回到本文件的“需求覆盖核对”，确保无遗漏

## 项目代码存放目录结构规划

为保证前端、后端、数据库三方协作时目录清晰、边界明确，建议项目根目录采用以下结构。该结构强调“按职责拆分”“共享约定集中管理”“数据库脚本可追溯”，便于后续部署与持续迭代。

### 目录职责说明

- 前端：仅承载页面、交互与接口适配，不直接写业务规则；业务规则以“后端返回”为准
- 后端：承载报名校验、战绩拉取与缓存、评分、分队、赛程、发布与周期清理等核心规则
- 数据库：承载建表、变更与初始化脚本，保证按周周期清理与可选归档的可执行性
- 共享：承载三方对接所需的“统一名词、字段结构、校验规则、业务码口径”，避免口径漂移
- 文档：承载落地文档与后续补充说明

## 统一名词与字段口径

### 统一名词

- 玩家：参与赛事并提交报名信息的个人
- 管理员：拥有管理后台权限的赛事组织者
- 报名：玩家提交战网标识、职责偏好等信息的行为
- 职责：重装、输出、支援三类位置偏好，可多选或设置主次
- 战绩快照：从第三方战绩服务拉取并缓存的结构化数据，用于评分与分队
- 评分：从战绩快照计算得到的综合实力分，用于队伍平衡
- 分队：按职责合规与实力均衡原则，将报名玩家分配到若干队伍
- 赛程：由队伍生成的对局安排，可发布到公开看板
- 看板：面向玩家展示队伍结果与赛程信息的页面
- 周期：以一周为生命周期的数据窗口；周期结束后执行清理或归档
- 清理：对本周期数据进行快速清空，进入下一周期

### 关键字段（中文口径）

- 战网标识：玩家唯一标识，格式为“名称井号数字”
- 职责偏好：玩家选择的职责集合与主次偏好
- 报名时间：报名提交的时间戳
- 周期标识：用于区分每周数据窗口的编号或开始日期
- 战绩来源时间：战绩快照拉取时间戳
- 分队版本：每次生成分队结果的版本号，便于回滚与追溯
- 发布状态：赛程与队伍是否已对外公开

## 三方对接统一约定（最小可落地口径）

本节用于确保前端、后端、数据库三方在字段与流程上能够无歧义对接。若后续要调整口径，应优先修改“共享”目录下的约定，并同步三份落地文档。

### 通用返回体（建议）

- 是否成功：布尔值
- 业务码：数字
- 提示信息：中文短句
- 数据体：对象或空

### 职责偏好结构（建议）

- 职责列表：由“重装、输出、支援”组成的集合
- 主职责：可选，若填写必须属于职责列表
- 次职责列表：可选，若填写必须属于职责列表，且不与主职责重复

### 周期口径（建议）

- 周期标识：由后端统一生成并作为数据库分区口径；前端仅展示，不自行推导
- 当前周期：后端提供查询接口返回，避免前端与数据库出现跨周误差

### 发布口径（建议）

- 队伍与赛程均区分“草稿”与“已发布”
- 看板仅展示“已发布”的最新版本

## 端到端流程总览

1. 玩家在报名页填写战网标识与职责偏好并提交
2. 后端校验：格式校验、真实性校验、重复报名校验、频次限制、人机验证校验
3. 管理员在后台查看报名列表，发起“批量拉取战绩”
4. 后端批量拉取战绩并缓存，计算评分并在后台可视化展示
5. 管理员发起“智能分队”，系统生成队伍与分队版本
6. 管理员发起“生成赛程”，选择赛制并生成对局
7. 管理员发布队伍与赛程，看板对外展示
8. 周期结束后，管理员执行“结束本周赛事”，系统进行清理或归档
